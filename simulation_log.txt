NOTE ON TOOLING (read this first)
---------------------------------------------------------------------
Icarus Verilog implements only a partial subset of SystemVerilog.
It does NOT support: constraint blocks, randomize(), covergroups,
clocking blocks, mailbox/semaphore classes, or virtual interfaces as
class members — the OOP verification constructs used by the
industry-standard class-based files in this repo (apb_transaction.sv,
apb_generator.sv, apb_driver.sv, apb_monitor.sv, apb_scoreboard.sv,
apb_coverage.sv, apb_env.sv, apb_if.sv, tb_top.sv). Those files are
written for and verified against Questa/VCS/Xcelium syntax (and will
run as-is on EDA Playground with a Questa/VCS backend).

tb_top_iverilog.sv is a task/procedural re-implementation of the SAME
verification methodology (generator, driver, self-checking scoreboard
with reference model, manually-tracked functional coverage bins,
weighted constrained-random-style stimulus) written to run on the
free, fully offline Icarus Verilog toolchain, so this log reflects a
real, reproducible simulation run rather than a simulator that
silently accepted unsupported syntax.

---------------------------------------------------------------------
BUG FOUND AND FIXED DURING BRING-UP (worth mentioning in interviews)
---------------------------------------------------------------------
First simulation attempt (pre-fix) result: PASS=103 FAIL=97, and the
"PSLVERR observed" coverage bin showed 0 hits despite 34 out-of-range
accesses actually occurring on the bus.

Root cause: the driver task sampled prdata/pslverr with a *blocking*
read in the same simulation time step in which the DUT updates those
signals with a *nonblocking* assignment. Because nonblocking (NBA)
updates are applied strictly after blocking (Active-region) reads in
the same delta cycle, the testbench was reading the value of prdata
left over from the previous transaction — a classic read-before-write
race condition.

Fix: added a 1-timestep delay (#1) after the sampling clock edge,
before reading prdata/pslverr, so the DUT's registered outputs settle
first. This is exactly the race that SystemVerilog `clocking block`
input skew (e.g. `input #1step`) is designed to eliminate by
construction — which is why the class-based version of this testbench
(apb_if.sv) uses a clocking block for its monitor/driver sampling
instead of a manual delay. Finding this race by hand is a good
example to walk an interviewer through: it demonstrates understanding
of *why* clocking blocks exist, not just that the keyword is required
syntax.

Post-fix result: PASS=200 FAIL=0, 8/8 coverage bins hit.

SECOND BUG FOUND ON MODELSIM (Intel FPGA Edition) — WORTH MENTIONING TOO
---------------------------------------------------------------------
Tool: ModelSim - Intel FPGA Edition, vlog/vsim 2020.1

Note: this edition does NOT hold a verification license, so it cannot
run the class-based OOP testbench (apb_transaction.sv -> tb_top.sv) at
all:

  ** Error: (vsim-1) Unable to checkout verification license -
  testbench generation feature (randomize, randcase, randsequence,
  covergroup) is only supported with QuestaSim.

This is a licensing limitation of the free/bundled edition, not a bug
in the code. tb_top_iverilog.sv (no randomize/covergroup/constraint)
was used instead, and it compiled and loaded cleanly.

Running tb_top_iverilog.sv on this ModelSim edition surfaced a SECOND,
real, timing-dependent scoreboard bug that Icarus's particular random
sequence had not happened to expose:

  SCOREBOARD REPORT: PASS=193 FAIL=7 TOTAL=200

All 7 failures were reads of address 0x0 where the expected value had
bit[31] set but the DUT returned bit[31] = 0, e.g.:
  FAIL: read mismatch addr=0x0 exp=0xa95ed63d got=0x295ed63d

Root cause: this is exactly the reference-model gap that had been
called out as a known limitation earlier in this document — the
scoreboard was not modeling register 0's 2-cycle self-clearing
bit[31]. Icarus's specific pseudo-random sequence never happened to
read register 0 shortly after writing it with bit[31] set, so the gap
stayed latent; ModelSim's different `$urandom` sequence did trigger
it, exposing the exact case that had been predicted.

Fix (in check_txn, tb_top_iverilog.sv): every APB transaction here
takes 3 clock edges (SETUP/ACCESS/sample), so by the time ANY
subsequent read transaction executes, at least one full extra
transaction has elapsed since the write's ACCESS edge — more than the
DUT's 2-cycle self-clear delay. A directed test confirmed this
directly: write reg0 with bit[31] set, then read reg0 on the very next
transaction -> bit[31] reads back as 0 every time. So the reference
model now always expects bit[31] == 0 for reads of register 0,
regardless of what was last written to it. Re-verified with 3 repeated
runs post-fix: PASS=200 FAIL=0 every time.

Interview takeaway: a documented, predicted reference-model limitation
was later triggered by a different simulator's random sequence,
root-caused with a small directed test, and fixed with a one-line
timing-aware masking rule — a realistic example of how corner cases
surface across regression runs with different random seeds/tools, and
why "known limitations" sections in verification docs matter.
