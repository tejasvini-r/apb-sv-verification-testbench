BUG FOUND DURING FIRST MODELSIM RUN (fixed before this final run)
---------------------------------------------------------------------
The very first run on this tool, using the same tb_top_iverilog.sv
before a reference-model fix, produced:

  SCOREBOARD REPORT: PASS=193 FAIL=7 TOTAL=200

All 7 failures were reads of register 0 where the expected value had
bit[31] set but the DUT returned bit[31] = 0, e.g.:
  FAIL: read mismatch addr=0x0 exp=0xa95ed63d got=0x295ed63d

This was a real, latent gap in the scoreboard's reference model: it
was not modeling register 0's documented 2-cycle self-clearing
bit[31] behavior. This exact limitation had already been called out
as a "known limitation" before this run, and this ModelSim run's
particular $urandom sequence was the first one (across Icarus and
ModelSim runs) to actually exercise the case that exposed it - Icarus's
random sequence in earlier runs happened not to read register 0 soon
enough after writing it with bit[31] set to trigger a visible
mismatch.

Root cause, confirmed with a small directed test (write reg0 with
bit[31] set, then read reg0 on the very next transaction): bit[31]
always reads back as 0, because at 3 clock edges per APB transaction,
by the time any subsequent read executes, more than the DUT's 2-cycle
self-clear delay has already elapsed.

Fix: the reference model's read-check for register 0 now always masks
bit[31] to the expected value 0, regardless of what was last written.
Re-verified: 200/200 pass on this run, and previously reconfirmed
200/200 across 3 repeated runs on Icarus Verilog too.
